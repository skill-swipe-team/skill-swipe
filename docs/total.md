# Проект «Система автоматизированного подбора эксперта на стартап-проекты»

## 1\. Обоснование выбора проекта

### **1.1. Контекст выбора**

Проект выбран командой, отдельное сравнение с другими кейсами не оформляется. Ниже приведены критерии и оценка выбранного проекта.

### **1.2. Проблема**

По разбору посмертных заметок закрывшихся стартапов от CB Insights, 23% компаний (выпуск 2017 года) назвали одной из причин «не ту команду»; в более позднем выпуске на 111 заметках эта доля составила 14%. Для сравнения: 42% закрылись из-за отсутствия рыночной потребности и 29% из-за нехватки денег (причины пересекаются, поэтому сумма больше 100%). Значит, подбор нужных людей остается одной из главных проблем ранних стартапов. Эти данные не измеряют именно поиск экспертов, поэтому гипотезу о боли пользователей необходимо проверить в 3-5 интервью (раздел 3).

_Источники:_ [_CB Insights, «The Top 20 Reasons Startups Fail» (2017)_](https://www.cbinsights.com/reports/The-20-Reasons-Startups-Fail.pdf)_, в пересказе Angel Capital Association и Quake Capital; SmartCompany, разбор отчета CB Insights о 111 посмертных заметках._

• Основатели стартапов на ранней стадии не могут быстро найти экспертов (разработчиков, аналитиков, дизайнеров, ML-инженеров), готовых принять участие в проекте по навыкам, времени и условиям.

• Эксперты не видят, какие проекты им подходят: информация разбросана по чатам, соцсетям и биржам.

• Существующие подходы (общие соцсети для профессионалов, биржи фриланса, чаты сообществ) требуют долгого ручного поиска и длинных форм. Отклик односторонний: одна сторона ищет, другая ждет.

### **1.3. Предлагаемое решение**

Telegram-бот с мини-приложением (Mini App) и механикой свайпов. Эксперт и владелец проекта видят ленту карточек, свайпают вправо при интересе. При взаимном интересе возникает мэтч и открывается чат. Навыки автоматически извлекаются из профилей, описаний проектов и резюме (ML-1). Лента ранжируется двусторонним матчингом с учетом истории свайпов (ML-2). Модели не обучаются: используются LLM и эмбеддинги через OpenRouter, история свайпов влияет на ранг через веса и повторное ранжирование.

### **1.4. Критерии выбора и оценка**

| Критерий | Вес | Оценка проекта (1-5) | Комментарий |
| --- | --- | --- | --- |
| Ценность для пользователя | 25% | 4 | Понятная боль, быстрый сценарий, низкий порог входа |
| Соответствие составу команды (2 ML, backend, аналитик) | 25% | 5 | Две независимые ML-задачи, четкое разделение зон ответственности |
| Реализуемость за 3 модуля | 20% | 4 | MVP можно собрать без ML, ML подключается слоями (подтверждено), без обучения: LLM через OpenRouter |
| Покрытие требований курса | 15% | 5 | Более 5 сущностей, более 5 эндпоинтов, естественные доп. сценарии (уведомления, фильтры, отчеты) |
| Измеримость результата | 10% | 5 | Конверсия свайп → мэтч, качество ранжирования, точность извлечения навыков |
| Риски (чем ниже риск, тем выше балл) | 5% | 3 | Холодный старт, нехватка данных, зависимость от внешнего LLM-сервиса, один full stack на весь frontend |

**Взвешенная оценка: около 4,4 из 5** (расчет предварительный).

### **1.5. Основные риски выбора**

• Холодный старт: без истории свайпов ранжирование не обучить. Решение: стартуем с правилами на пересечении навыков, затем подключаем LLM и эмбеддинги через OpenRouter без обучения; синтетические данные для демо.

• Отсутствие реальных пользователей: нужны тестовые профили и 3-5 интервью.

• Один full stack разработчик закрывает весь frontend и часть backend: риск перегрузки.

• Персональные данные в резюме уходят во внешний LLM-сервис: нужны согласие, маскирование контактов и ограничение доступа.

## 2\. Границы проекта и глоссарий

**В проекте (in scope):** вход через Telegram, профили экспертов, проекты, лента, свайпы, мэтчи, чат, извлечение навыков, ранжирование, три Telegram-бота (свайпы, чат, жалобы) и Mini App, ручная модерация жалоб командой, выбор языка интерфейса.

**Вне проекта (out of scope):** оплата и платные тарифы, видеозвонки, отдельный веб-сайт и мобильное приложение, панель администратора, обучение собственных моделей, групповые чаты, юридическое оформление сотрудничества, оценка стартапа как бизнеса.

| Термин | Определение |
| --- | --- |
| Эксперт | Пользователь, ищущий проекты для участия |
| Владелец проекта | Пользователь, ищущий экспертов |
| Профиль | Данные эксперта: описание, навыки, опыт, доступность, резюме |
| Проект | Карточка стартапа: описание, стадия, требуемые навыки, формат участия |
| Навык | Нормализованная сущность из справочника (например, Python, UX-исследования) |
| Свайп | Решение пользователя по карточке: вправо (интерес) или влево (пропуск) |
| Мэтч | Взаимный интерес эксперта и владельца проекта |
| Лента | Ранжированный список карточек для пользователя |
| Скор релевантности | Число от 0 до 1, оценка пары «эксперт-проект» моделью ML-2 |
| Боты | Три Telegram-бота: бот свайпов (вход, профиль, лента, уведомления), бот чата (переписка участников мэтча), бот жалоб (прием жалоб) |
| Mini App | Веб-приложение внутри Telegram: профиль, проекты, лента со свайпами |
| OpenRouter | Сервис доступа к LLM и моделям эмбеддингов по единому API |
| Режим | Текущая роль пользователя: «ищу проекты» (эксперт) или «ищу экспертов» (владелец проекта); переключается кнопкой в меню |
| Скрытие пользователя | Личное решение: скрытый пользователь больше не появляется в ленте и чатах того, кто его скрыл |
| Блокировка | Запрет пользоваться сервисом для конкретного Telegram ID; ставится командой вручную. Сам Telegram-аккаунт при этом не затрагивается |

Между Swipe и Match внешнего ключа нет: мэтч возникает логически из двух свайпов вправо по одной паре (связь 2 : 1).

**Правило мэтча:** Match создаётся, когда для пары (expert\_id, project\_id) есть Swipe от эксперта и Swipe от владельца, оба с direction = right.

**Правила целостности, которые не выражаются внешним ключом:**

1.  Самоматч запрещён: владелец проекта (Project.owner\_id) не может быть экспертом в паре (expert\_id) для того же проекта.
2.  Отправитель сообщения должен быть участником мэтча: Message.sender\_id равен expert\_id мэтча или владельцу его проекта.
3.  Мэтч создаётся только при двух свайпах вправо по паре; при отмене свайпа до мэтча (US-23) запись Swipe удаляется.
4.  Скрытие: blocker\_id не равен blocked\_id.
5.  В жалобе заполнено хотя бы одно из полей target\_user\_id и target\_project\_id.
6.  При удалении аккаунта (US-17) каскадно удаляются ExpertProfile, Resume, Project, ExpertSkill, ProjectSkill, Swipe, Match, BotStart и Embedding; в Message, Report, EventLog и LlmCall ссылка на пользователя обнуляется, чтобы история осталась обезличенной.

**Пример: свайп.**

Запрос POST /swipes:

{ "project\_id": 42, "expert\_id": 7, "direction": "right" }

Ответ 201 (мэтча нет):

{ "swipe\_id": 1001, "matched": false }

Ответ 201 (мэтч):

{ "swipe\_id": 1002, "matched": true, "match\_id": 310 }

Коды ошибок: 400 неверный формат, 401 нет токена, 403 нет права на проект, 404 объект не найден, 409 повторный свайп (возвращается сохраненный результат).

**Пример: лента эксперта.** GET /feed?limit=2, ответ 200:

{ "items": \[ { "project\_id": 42, "title": "Сервис учета склада", "stage": "MVP", "skills": \["Python", "PostgreSQL"\], "score": 0.82, "why": \["Python", "PostgreSQL"\] } \], "next\_cursor": "abc" }

**Контракт ML-1 (извлечение навыков), внутренний.** POST /ml/skills/extract:

{ "text": "...текст резюме или описания...", "source": "resume" }

Ответ: { "skills": \[ { "name": "Python", "confidence": 0.93 } \], "model\_version": "0.1" }.

**Контракт ML-2 (ранжирование), внутренний.** POST /ml/rank:

{ "subject": { "type": "expert", "id": 7 }, "candidate\_ids": \[42, 43, 44\] }

Ответ: { "ranking": \[ { "id": 42, "score": 0.82 }, { "id": 44, "score": 0.55 } \], "model\_version": "0.1" }. Если ML недоступен, backend использует правиловое ранжирование.

## 16\. Telegram и LLM: решения аналитика (обоснование)

Три Telegram-бота (свайпы, чат, жалобы) плюс Mini App, один аккаунт на Telegram ID и ML на LLM без обучения: так проект реализуем силами одного backend, одного full stack и двух ML-инженеров за три модуля.

### **16.1. Интерфейс: бот и Mini App**

| Компонент | Что делает |
| --- | --- |
| Бот | Три бота. Бот свайпов (основной): вход (/start), согласие, меню (/menu, /profile, /feed, /matches, /help), открытие Mini App, уведомления о мэтчах, дайджест, прием резюме файлом. Бот чата: пересылает сообщения между участниками мэтча. Бот жалоб: принимает жалобы, сохраняет и пересылает команде |
| Mini App | Веб-приложение, которое открывается кнопкой из бота: профиль и навыки, создание проекта, лента со свайпами, список мэтчей |

Почему так: не нужна установка и регистрация, push-уведомления доступны без дополнительной настройки, а полноценный свайп возможен только в Mini App. Запасной вариант, если реализация Mini App не укладывается в сроки: лента карточками с inline-кнопками «Интересно» и «Пропустить» прямо в боте, frontend тогда сильно меньше.

### **16.2. Аккаунт и вход**

Идентификатор пользователя это Telegram ID. Mini App передает backend подписанные данные запуска (initData), backend проверяет подпись токеном бота, находит или создает пользователя и выдает JWT. Паролей, email и восстановления доступа нет. Один аккаунт работает в двух режимах: эксперт и владелец проекта. Текущий режим хранится в поле active\_mode, выбирается при первом /start и переключается кнопкой в меню. Роль отдельно не хранится: действие разрешено, если у человека есть нужная сущность (профиль эксперта или проект). Профиль эксперта создается при первом входе в режим эксперта. Лента исключает проекты, владельцем которых является сам пользователь, поэтому самоматч невозможен.

### **16.3. Чат через бота**

При мэтче бот свайпов присылает обеим сторонам сообщение «Это мэтч» с кнопкой-ссылкой на бота чата. Telegram не позволяет боту написать пользователю первым, поэтому каждый участник один раз нажимает Start в боте чата. Сообщение, отправленное боту чата в диалоге мэтча, бот пересылает собеседнику от своего имени с подписью (имя и проект) и сохраняет в таблице Message. Если у пользователя несколько диалогов, активный выбирается кнопкой из списка.

• Плюсы: не нужны WebSocket, username и обмен контактами; история остается у нас для метрик и жалоб; доставку в реальном времени обеспечивает Telegram.

• Минусы: нет статуса «прочитано», действуют лимиты Telegram на отправку (порядка 30 сообщений в секунду на бота и около 1 в секунду на чат), нет богатого интерфейса чата.

• Расширение (Would, US-22): кнопка перехода в личный диалог по ссылке t.me/username для пользователей, которые разрешили показывать username.

### **16.4. ML на LLM без обучения**

**ML-1, извлечение навыков.** Текст резюме (после извлечения из PDF или DOCX), профиля или описания проекта → маскирование телефонов и email → запрос в OpenRouter с промптом и JSON-схемой → список навыков с оценкой уверенности → нормализация по справочнику (точное совпадение, синонимы, ближайший по эмбеддингу выше порога) → показ пользователю на подтверждение. Качество проверяем на 30 размеченных примерах (полнота, точность и F1, см. NFR-07).

**ML-2, двусторонний матчинг и ранжирование.**

1\. Отбор кандидатов запросом к БД: активные, непросмотренные, незаблокированные, с пересечением навыков.

2\. Оценка пары как среднее гармоническое двух оценок: «эксперт подходит проекту» и «проект подходит эксперту». Каждая оценка это взвешенная сумма: покрытие обязательных навыков, близость эмбеддингов описаний, совпадение формата участия и доступности.

3\. Учет свайпов без обучения: прибавка за близость к усредненному эмбеддингу понравившихся карточек и штраф за близость к пропущенным.

4\. (Should) LLM-переранжирование первой десятки с короткой причиной, которая показывается как объяснение релевантности.

5\. Результаты хранятся в RecommendationScore, пересчитываются при новом свайпе или смене профиля и фоном; лента читает кэш. На холодном старте работают только шаги 1-2.

Эмбеддинги: через OpenRouter, если у выбранной модели есть такой метод, иначе небольшая локальная модель (sentence-transformers) в контейнере; проверить на спринте 2 \[TBD\]. Хранение: pgvector. Оценка ML-2: синтетический набор пар (профили и проекты генерирует LLM с известной эталонной разметкой), метрика NDCG@10 против правилового ранжирования.

### **16.5. Риски внешнего LLM и меры**

| Проблема | Мера |
| --- | --- |
| Стоимость | Бесплатные модели или лимит расходов на ключе, кэш, дедупликация по хэшу текста; учет лимита бесплатных запросов (20 в минуту, 50 или 1000 в сутки) |
| Задержки | Асинхронные вызовы, очередь, таймаут 10 секунд, лента из кэша |
| Нестабильный формат ответа | JSON-схема, temperature 0, до 2 повторов, валидация |
| Конфиденциальность | Согласие, маскирование контактов, отправка только нужного текста |
| Недоступность сервиса | Запасной путь: правила и ручной ввод навыков |
| Воспроизводимость | Модель и версия промпта пишутся в LlmCall |

### **16.6. Предлагаемый стек**

| Слой | Выбор | Почему |
| --- | --- | --- |
| Backend | Python, FastAPI | Один язык для API, бота и работы с LLM |
| Бот | aiogram 3, три webhook (по одному на бота) в одном сервисе | Зрелая библиотека, поддержка Mini App |
| БД | PostgreSQL, pgvector | Связи, ограничения уникальности, векторный поиск |
| Очереди и кэш | Фоновые задачи в процессе, Redis при необходимости | Минимальная сложность на старте |
| Frontend | React или Vue, Vite, SDK Telegram Mini Apps | Привычный стек, быстрая сборка |
| Инфраструктура | Docker Compose, CI в Сфера.Код, сервер с публичным HTTPS | Webhook бота требует HTTPS |

### 16.7. Три бота: кто за что отвечает

| Бот | Назначение | Что делает пользователь | Что делает бот |
| --- | --- | --- | --- |
| Бот свайпов (основной, к нему привязан Mini App) | Вход, профиль, лента, свайпы, мэтчи | Нажимает Start, принимает согласие, пользуется меню и Mini App | Сообщает о мэтчах, присылает дайджест, принимает резюме файлом |
| Бот чата | Переписка внутри мэтча | Переходит по ссылке из сообщения о мэтче, нажимает Start и пишет | Пересылает сообщения собеседнику и хранит историю |
| Бот жалоб | Ручная модерация | Нажимает «Пожаловаться», в боте жалоб описывает причину | Сохраняет жалобу и пересылает ее команде |

У всех трех ботов один backend (один сервис с тремя webhook), поэтому пользователь определяется одним Telegram ID, а данные общие. Переход между ботами делается ссылками со служебным параметром (например, ссылка на бота чата с номером мэтча) и одним нажатием Start.

### 16.8. Языки интерфейса

Тексты ботов и Mini App не пишутся в коде, а хранятся во внешних словарях по ключам сообщений. Язык по умолчанию берется из настроек Telegram, пользователь может сменить его кнопкой, а новый язык добавляется новым файлом словаря без изменения кода. Даты, числа и время форматируются по региону пользователя. Названия навыков в справочнике хранятся в нескольких языках, поэтому поиск совпадений не зависит от языка интерфейса.
